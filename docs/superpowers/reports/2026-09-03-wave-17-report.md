## Final whole-branch review

Per the wave's own execution process, a final review covered the entire branch diff (43
commits, 101 files, ~10,700 insertions) at once — the one vantage point no per-task review has.
It confirmed clean: the `CapabilityRegistry`/`DefectFlags` double-bookkeeping anti-pattern Task
5/7 eliminated did not reappear anywhere across all 15 archetypes; no fabricated NFR citation
exists anywhere in the diff; and `IdempotencyService` (Task 25) and `DeliveryService`'s dedup
gate (Task 26) — the wave's two safety-critical pieces of logic — were independently re-derived
from a fresh read and confirmed correct.

It also found real problems only a whole-branch view could surface: two of the eight new
modules had invariants that could never fail, one convention drift with a real 4-hour CI-hang
risk, and a handful of narrower, non-blocking issues. **Fixed before this report was finalized**
(commits `fc09f32`, `bf94bb7`, both independently re-verified against a live rebuilt stack, not
just read):

- **TST-029's I5 was a mathematical tautology.** `dlqExported && (observedDepth > alertDepth ?
  alertFiring : !alertFiring)` reduced to `X ? X : !X` — always `true`, because `alertFiring`
  and the ternary's own condition were the same boolean computed by the SUT from the same
  response. Fixed by comparing two genuinely different snapshots (the alert's state before the
  poison burst, when depth is 0, against its state after, when depth exceeds the threshold) —
  now falsifiable, and confirmed to genuinely fail under `dlq-bypass-drop`.
- **TST-034's I1 was forced to `passed` under smoke mode without evaluating anything real.**
  Fixed to report `not-evaluated` honestly, matching the pattern this same module and two others
  already used correctly for invariants a 20-second smoke run cannot measure.
- **TST-034 hardcoded raw `System.getenv("HARNESS_SMOKE_MODE") == "true"`** in four places
  instead of the established `HarnessConfig.smokeMode()` single source of truth (which accepts
  `1`/`yes`/`on` case-insensitively) — a real risk that an operator using any of those other
  accepted values would trigger a 4-hour hold instead of a 20-second one. Fixed to route through
  the same profile-driven, `HarnessConfig`-driven computation the rest of the harness uses.
- **TST-034 also hardcoded its `20`/`14400` hold-duration literals** directly in `plan.jmx`
  instead of reading them from `ProfileResolver.Profile` (the exact mechanism Task 11 built to
  prevent this). Fixed in the same change as the point above — `mixed.yml`'s declared values are
  unchanged, only their source is now real.
- The stale "7 capabilities implemented" count in `qe-harness/README.md` (see below).
- A follow-on doc correction the scoped re-review of the above caught: `tst-034-blend/README.md`
  still claimed I1 "passes" under the exact smoke-mode defect-proof scenario its own example
  runs, contradicting the fix above. Corrected.

**Deliberately not fixed in this pass — parked as disclosed follow-ups** (each fully diagnosed
with file:line evidence, reversible, none load-bearing for what this wave shipped):

- `AggregatorService.emit()` publishes to `qe.in` with routing key `"aggregate"`, which has no
  binding — every aggregate emission is silently unroutable. TST-028 reads its verdict from an
  in-memory map over HTTP, not the broker, so no shipped invariant depends on this broken leg,
  but the next wave that adds an aggregate-side broker consumer will need this fixed first.
  Relatedly, `qe.q.branch.{a,b,c}` accumulate unboundedly across runs (unlike every other queue
  this wave's services purge on `reset()`).
- `tst-028-fanout/README.md` still describes the two-role design that predates Task 22's
  mid-task redesign into three roles (`reference`/`timedout`/`dedup`); the assertion script's
  own header comment is accurate, only the README lagged.
- `TST-023` claims `coverage: full` while never assessing the archetype's own I6 ("no reservation
  outlives its declared TTL") — not `not-evaluated`, not disclosed anywhere. The SUT-side
  mechanism (`ReservationSweeper`) exists and is unit-tested; what's missing is a harness-level
  invariant check, which is a real (if small) piece of new work rather than a same-session fix.
